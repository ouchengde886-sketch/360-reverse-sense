### 2.2 查杀引擎调用（本轮打通）

**这是本轮最重要的产出。** 修复前 `scan_ave()` 对所有文件返回 `EXC`，病毒和干净文件返回值完全相同，等于没有判别能力。

**根因（三层）**：

1. `av_ave_scan32.ps1` 用 `try { Add-Type ... } catch { }` **静默吞掉异常**；
2. `Add-Type` 在本机**必然失败** —— 360 的文件系统微过滤驱动按扩展名拦截 `.dll` 写入，而 `Add-Type` 必须写临时 `.dll`，报
   `Access to the path '...\xxxxxxxx.dll' is denied.`；
3. 类型 `[AveScan]` 从未加载 → 后续每个调用抛 `TypeNotFound` / null 异常 → 脚本统一映射成 `EXC`，**把全部诊断信息丢光**。

**修复方案**（已验证）：
```powershell
try {
  Add-Type -TypeDefinition $sig -ErrorAction Stop
} catch {
  # .com 不被 PE 拦截规则覆盖；LoadFile 不检查扩展名
  $comPath = Join-Path $env:TEMP ("avtype_" + [guid]::NewGuid().ToString('N') + ".com")
  Add-Type -TypeDefinition $sig -OutputAssembly $comPath -ErrorAction Stop
  [void][System.Reflection.Assembly]::LoadFile($comPath)
}
```

**修复效果**：

| 测试 | 修复前 | 修复后 |
|---|---|---|
| `test_ave_engine.py` | 4/12（全 `EXC`） | **12/12** |
| `test_qex_api.py` | 0/13 | **13/13** |
| `test_nonpe_engine.py` | 0/11（崩溃） | **11/11** |

引擎现在能真实解析 PE：完整 `notepad.exe` → `clean status=0`；截断/坏 MZ/全零/随机字节 → `status=4`；不存在 → `status=251`。

**注意**：AVE 引擎**只处理 PE**。官方日志里那 7 个真实威胁（`.ps1`/`.zip`/`.txt`）走的是 **QEX 脚本引擎**，不是 AVE。AVE 对它们返回 `status=4` 是**正确行为，不是漏报**。

### 3.1 从记录里能读出的东西

| 字段 | 含义 | 依据 |
|---|---|---|
| `FD` | **File Defense**（文件防护） | 动作是"修改"，路径是文件 |
| `AD` | **Application Defense**（程序防护） | 动作是"进程创建" |
| `FD\|57, 1430\|...` | 规则 ID / 内部参数 | 结构未解 |
| `AD\|1, 10001\|10, 10, 60` | 规则 ID + 三个数（疑似计数/超时） | 结构未解 |

**关键观察**：

1. **它连无害操作都拦。** `Invoke-Shellcode.ps1` 是我自己测试目录里我自己创建的文件；`powershell.exe` 是微软签名的系统程序。360 照样拦。
2. **`AD` 拦的是"父进程启动子进程"这个动作本身**，不是子进程有问题。`DeepSeek Harness.exe → powershell.exe` 被拦，理由是"如果您不认识此程序"。
3. **`AD|1, 243|10, 60, -1` 拦的是 `powershell.exe → cmd.exe`。** 连启动 cmd 都要问。

### 3.2 这推翻了什么

我此前写下的结论：

> "360 的主动防御对内存注入与网络完全不设防"

**这个说法是错的（或者说，是废话）。**

- `VirtualAllocEx`、`CreateRemoteThread`、`connect()` 是**正常程序天天在用的 API**。任何杀软都不会拦这些，否则浏览器都开不起来。所以"不拦"不是发现。
- **真正该被拦的是"这个 PE 是病毒"这件事** —— 而我全程没测过。
- 用户记录证明：**360 拦的是"进程创建"这个动作**（`AD`），而不是"内存操作"。

### 3.3 最有价值的线索

`AD|1, 10001|10, 10, 60` 和 `AD|1, 243|10, 60, -1` 里的数字，**很可能就是"询问用户"的超时/计数参数**。

用户说过：

> "你研究时 要感知拦截 我都点了几次暂不处理了"

**"暂不处理"就是那个未应答的询问。** 这能解释为什么 `.exe` 拦截时灵时不灵 —— 不是规则不稳定，是**在等一个没人给的回答**。

## 6. 已更正的误判（9 项，血泪教训）

| 原结论 | 真实原因 |
|---|---|
| `ZhuDongFangYu.exe` 不可读 | 路径写错，实际可读 |
| `Start-Process` 被拦 | 未被拦，9 种场景全成功 |
| 360 目录不可写 = 保护 | Windows 标准 ACL + 未提权 |
| `HKLM` 只读 = 保护 | Windows 标准 ACL + 未提权 |
| 注入原语返回 `False` = 被拦 | ctypes 未设 `argtypes`，指针被截断 |
| `VirtualAllocEx` 被选择性拦 | `STATUS_PROCESS_IS_TERMINATING`（进程正在退出）|
| 右键扫描只写 ScanCache 不写日志 | 落点由 360 内部路径决定 |
| PE 后缀拦截 = 文件被独占占用 | **反了：两者都存在，是两种独立原因** |
| 引擎返回 `EXC` = 引擎不响应 | **`Add-Type` 被 `.dll` 拦截而静默失败** |

### 6.1 方法论教训（写给下一个接手的人）

1. **"API 返回失败" ≠ "被安全软件拦截"**。必须取真实错误码（用 `ntdll` 原生调用拿 `NTSTATUS`，不是 `GetLastError()`），并做**同条件对照实验**。
2. **"API 返回成功" ≠ "安全软件放行"**，也可能是**它根本没在看**。这是本次最大的教训 —— 见 §0。
3. **不要用 `catch { }` 吞异常**。本轮为此浪费了大量时间：引擎"不响应"的真身是类型加载失败。
4. **`.ps1` 必须带 UTF-8 BOM**。PowerShell 5.1 对无 BOM 文件按 GBK 解读中文注释，多字节序列错位会**吞掉下一行代码**，表现为"某行代码凭空消失、变量为 `$null`"。本轮在这上面浪费了大量时间。
5. **PowerShell 变量名大小写不敏感且静默冲突**：`$args`、`$pid`、`$sig`、`$i` 都是雷。

## 7. 环境与工具约束（踩过的坑）

| 约束 | 说明 |
|---|---|
| 360 引擎是 **x86** | 必须用 `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`，64 位宿主报 `WinError 193` |
| **`Add-Type` 在本机不可用** | `.dll` 写入被拦。必须用 `.com` + `Assembly::LoadFile` |
| **Python `ctypes` 是唯一可靠的 P/Invoke 路径** | 不写 `.dll`，不受拦截影响 |
| WOW64 重定向 | 32 位宿主访问 `System32` 会被重定向，需用 `Sysnative` |
| `NtXxx` 的 `NTSTATUS` 才是可靠判据 | `0xC000010A`=进程正在退出，`0xC0000022`=拒绝访问；`GetLastError()` 会误导 |
| PowerShell 5.1 无内联 `if` 表达式 | 用 `$(if ...)` |
| `git commit -m` 带引号会失败 | 用 `git commit -F <文件>` |
